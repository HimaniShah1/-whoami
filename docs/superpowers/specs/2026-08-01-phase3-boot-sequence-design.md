# Phase 3: Boot Sequence — Design

## Context

This is Phase 3 of "Backend Odyssey," following Phase 1 (Foundation) and Phase 2
(Player & Camera Feel). Before the visitor ever moves the camera, they see a
cinematic terminal boot sequence — the site's version of a loading screen,
themed as their HTTP request being provisioned into the backend. `SKILLS.md`
already reserves `src/components/boot/` for this phase and designates GSAP
(a new dependency, installed in this phase) as the tool for exactly this kind
of multi-step cinematic timeline.

**Goal of this phase:** a full-screen, dark terminal overlay that plays before
`Experience`/`Hud` mount, showing personalized boot log lines (using the
visitor's actual generated `requestId`/`protocol`/`ttl`), a progress bar, and
a "Backend Ready" completion state, then hands off to gameplay.

## Scope Decisions

Resolved before this design:

- **Skippable, once per session.** Any keydown or click during boot jumps
  straight to completion. First page load in a browser session (tab or new
  session) plays the full sequence; a reload within the same session skips it
  entirely via `sessionStorage`, so repeated reloads during a visit aren't
  punishing.
- **Personalized content.** Boot lines reference the actual `requestId`,
  `protocol`, and `ttl` already generated by `useGameStore` on module load,
  rather than a fully generic script — ties directly into the HUD the visitor
  sees immediately after boot completes.
- **Reduced motion shows instantly, doesn't skip.** With
  `prefers-reduced-motion` set, all boot lines and the progress bar render
  fully visible immediately (no per-line reveal animation, no typewriter
  effect), then a brief pause before handing off to gameplay — the narrative
  content (request ID assignment, etc.) still gets shown once, just without
  motion.

## Architecture

Following the project's established split (pure logic → tested; imperative
animation/rendering → manually verified), Phase 3 introduces four small units:

- **`src/components/boot/bootScript.ts`** — pure function
  `buildBootScript(requestId: string, protocol: string, ttl: number):
  string[]`, returning an ordered array of boot log line strings, several of
  which interpolate the given identity values (e.g. `Assigning request ID:
  ${requestId}`). No React, no timing, no DOM — fully unit-tested.
- **`src/components/boot/TerminalOutput.tsx`** — presentational component.
  Props: `visibleLines: string[]`, `progress: number` (0-100), `done:
  boolean`. Renders the revealed lines, a blinking-cursor span after the last
  line (via CSS animation, suppressed when `done`), and a progress bar +
  percentage. Plain DOM, not R3F — unit-tested with React Testing Library,
  matching `Hud`/`WebGLUnavailable`/`ConnectionLost`.
- **`src/components/boot/BootSequence.tsx`** — orchestrator. Reads
  `requestId`/`protocol`/`ttl` from `useGameStore` (individual selectors) and
  `reducedMotion` from `useUIStore`, builds the script via
  `buildBootScript`, and owns a GSAP timeline that reveals lines one at a
  time and advances `progress` from 0 to 100, calling `onComplete()` at the
  end. A `keydown`/`click` listener attached for the duration of the sequence
  calls `timeline.progress(1)` (jump to end) to skip. When `reducedMotion` is
  true, the timeline duration collapses to near-zero (all lines appear
  immediately) rather than being skipped structurally — same code path,
  different timeline duration, so the "instant" and "skipped" cases can't
  drift apart into two different behaviors. No unit test — GSAP-driven
  imperative timeline, same bucket as `CameraManager`.
- **`src/lib/session.ts`** — `hasSeenBootSequence(): boolean` and
  `markBootSequenceSeen(): void`, thin wrappers over
  `sessionStorage.getItem`/`setItem` with a single shared key constant.
  Unit-tested by mocking `sessionStorage`, matching `lib/webgl.ts`'s pattern
  of mocking browser APIs.

**`AppRoot.tsx`** gains one new piece of state and one new gate, inserted
between the existing WebGL-readiness check and the `Experience`/`Hud`
render: after `webglReady` resolves true, if `!hasSeenBootSequence()`, render
`BootSequence` with an `onComplete` that calls `markBootSequenceSeen()` and
flips a local `bootDone` flag to `true`. `Experience`/`Hud` render once
`bootDone` is true (either because boot finished/was skipped, or because
`hasSeenBootSequence()` was already true on mount, in which case `bootDone`
starts `true` and `BootSequence` never mounts at all).

## Data Flow

```
useGameStore (requestId, protocol, ttl)  ──┐
useUIStore (reducedMotion)                ├──► BootSequence
                                           │      │
                              buildBootScript      │  GSAP timeline
                                    │               │  (reveals lines,
                                    ▼               │   advances progress)
                              string[] lines ───────┘
                                                     │
                                                     ▼
                                            TerminalOutput (renders)
                                                     │
                                    keydown/click ───┘ (skip → jump to end)
                                                     │
                                              onComplete()
                                                     │
                                    markBootSequenceSeen() + AppRoot flips
                                    bootDone → renders Experience + Hud
```

## Error Handling

No new failure surfaces. `sessionStorage` access is wrapped the same way
`lib/webgl.ts`/`lib/reduced-motion.ts` already guard browser APIs (a
`typeof window === 'undefined'` guard is unnecessary here since `AppRoot` is
already client-only and post-mount, but `hasSeenBootSequence`/
`markBootSequenceSeen` still wrap the calls in case `sessionStorage` throws —
e.g. Safari private browsing can throw on `setItem` — falling back to
treating the sequence as unseen rather than crashing).

## Testing

- `src/components/boot/bootScript.test.ts`: unit tests for
  `buildBootScript` — correct line count/order, correct interpolation of
  `requestId`/`protocol`/`ttl` into the expected lines.
- `src/components/boot/TerminalOutput.test.tsx`: RTL tests — renders the
  given `visibleLines`, shows the progress percentage, cursor present when
  `!done` and absent when `done`.
- `src/lib/session.test.ts`: unit tests for `hasSeenBootSequence`/
  `markBootSequenceSeen` against a mocked `sessionStorage`, including the
  case where `sessionStorage` throws.
- `BootSequence.tsx` and the `AppRoot.tsx` wiring: manually verified only
  (GSAP timeline + skip-key listener), consistent with the project's
  established convention for imperative/animation-driven components.

## Out of Scope (explicitly)

- The later "walk up, press E, terminal prints text" interaction pattern
  (Phase 4/6's `About Me` terminal, hidden terminals, Contact Gateway form) —
  a diegetic in-world 3D interaction, structurally different from this
  full-screen pre-gameplay overlay. Not unified into one component; revisit
  for shared primitives only if real duplication shows up once that pattern
  is built.
- Boot sequence audio (server hum starting, relay click sounds) — deferred to
  the Phase 14 audio pass per `SKILLS.md`'s Sound Strategy.
- Any change to `useGameStore`'s request-identity generation itself — this
  phase only reads the existing `requestId`/`protocol`/`ttl` fields.
